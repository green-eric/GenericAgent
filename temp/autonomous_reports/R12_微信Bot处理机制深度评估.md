# R13 - 微信Bot处理机制深度评估

> 自主行动 | 2026-05-05 | 分析微信 bot 完整处理链路，定位问题根源，提出统一方案

## 一、完整处理链路

```
用户微信消息 → iLink API → getUpdates → on_message() → 
  ├─ 天气快速通道（正则匹配城市名）→ wttr.in API → 格式化 → send_text()
  ├─ 命令处理（/stop /abort /llm）
  └─ LLM 推理（agent.run()）→ 流式输出 → send_text()
```

## 二、核心问题诊断

### 问题1：天气快速通道 — 硬编码格式，不可扩展
- 当前：在 on_message() 里用正则匹配城市名，手动拼字符串
- 问题：每个新场景都要写一套格式化逻辑，代码膨胀
- 证据：天气通道 ~100 行，全是 if/else 拼字符串

### 问题2：LLM 回复 — 无格式化，直接发送
- 当前：agent.run() 返回什么就发什么
- 问题：LLM 输出 Markdown（**粗体**、##标题、表格），微信不渲染
- 证据：用户反馈"没有换行"、"格式不对"

### 问题3：send_text() — 已有 _fmt_wx() 但覆盖不全
- 当前：send_text() 内部调 _fmt_wx()，但天气通道手动拼   绕过
- 问题：_fmt_wx() 在 line 441 的 _clean() 里被调用，但 send_text() 在 line 105 也调用了
- 证据：双重调用可能导致冲突

### 问题4：回复慢 — LLM 推理链路过长
- 当前：天气查询也走 LLM（agent.run()），LLM 再去查网页
- 问题：LLM 推理 5-30 秒，用户等不了
- 证据：用户反馈"甘肃天气到现在还没有回复"

### 问题5：英文回复 — LLM 默认英文
- 当前：agent 系统提示可能未强制中文
- 问题：天气查询返回英文
- 证据：用户反馈"I'll search for Gansu weather information"

## 三、与 GA 对话的差异

| 维度 | GA 对话（这里） | 微信 Bot |
|------|----------------|----------|
| 输出格式 | Markdown 渲染 | 纯文本，不渲染 Markdown |
| 换行 | \n 正常渲染 | 需要 \u2028 |
| 代码块 | 语法高亮 | 变成纯文本 |
| 表格 | 表格渲染 | 变成竖线分隔 |
| 响应速度 | 直接输出 | 经过 API 中转，延迟 +2-5s |
| 语言 | 中文 | 可能英文（LLM 未强制） |

## 四、改进方案（优先级排序）

### P0：天气快速通道优化
- 已有快速通道，但格式硬编码
- 建议：抽取 format_weather() 函数，统一格式化逻辑
- 预期：减少 50% 天气相关代码

### P1：LLM 强制中文 + 快速通道扩展
- 修改 agent 系统提示，强制中文回复
- 扩展快速通道：股票、新闻等高频查询不走 LLM
- 预期：回复速度从 5-30s 降到 1-3s

### P2：统一格式化出口
- 确认 _fmt_wx() 在 send_text() 的唯一调用点
- 移除 _clean() 中的重复调用
- 预期：消除双重格式化冲突

### P3：流式发送优化
- 当前：等 LLM 全部生成完再发
- 建议：分段发送，先回复"正在查询..."
- 预期：用户体验显著提升

## 五、风险评估
- 修改 send_text() 可能影响所有消息类型
- 修改快速通道可能引入新 bug
- 建议：每次只改一个点，测试后再继续

## 六、结论
微信 bot 的核心问题是 **格式化不统一** 和 **响应链路过长**。
已有 _fmt_wx() 是正确方向，但需要：
1. 确保所有消息都经过 _fmt_wx()
2. 高频查询走快速通道（不走 LLM）
3. LLM 强制中文
4. 流式分段发送
