## 二、架构评估

### 2.1 数据流架构 ✅ 优秀

```
AkShare → DataProvider → IndicatorCalculator → Scorer → Excel/Console
                ↓               ↓
           DataCache       防未来函数
          (SQLite)        (ann_date 过滤)
```

- **单向数据流**，层与层之间通过 DataFrame/Dict 传递，耦合度低
- **防未来函数**设计正确：使用 `ann_date`（公告日）而非 `report_date`（报告期）过滤，回测时保证只用已公告数据
- **一票否决**在 Scorer 层实现，逻辑集中

### 2.2 模块职责

| 模块 | 职责 | 评价 |
|------|------|------|
| `config.py` | 全局配置（权重/阈值/否决规则） | ✅ 清晰，集中管理 |
| `data_provider.py` | AkShare 三表获取 + 行情 + 行业 | ✅ 有 Fallback 链，字段映射完整 |
| `calculator.py` | 单季拆分 + TTM + 杠杆计算 | ✅ 逻辑严谨，有 pandas 3.x 兼容处理 |
| `scorer.py` | 五维评分 + 一票否决 | ✅ 评分逻辑清晰，否决规则集中 |
| `database.py` | SQLite 持久化（财报/行情/评分/股票信息） | ✅ 表结构完整，索引合理 |
| `utils_cache.py` | SQLite 缓存（JSON 格式存储） | ⚠️ 与 database.py 功能重叠 |
| `batch_runner.py` | 并发 + 限流 + 断点续跑 | ✅ 设计完善，但未集成到 main.py |
| `utils.py` | ST 过滤 / 日历 / 股票池加载 | ✅ 工具函数合理 |
| `main.py` | CLI + 评分 + Excel 导出 | ⚠️ 过于庞大（~800行），多职责混合 |

## 三、已识别的 Bug 和潜在问题

### 🔴 P0 — 运行时错误（会导致程序崩溃）

#### Bug 1：`main.py` `fetch_one()` 中 `global` 引用错误

**位置**：`main.py` 第 686-687 行

```python
def fetch_one(symbol):
    global success, fail  # ← BUG
```

**问题**：`success` 和 `fail` 是 `main()` 函数内的局部变量（第 683 行定义），不是模块级全局变量。`global` 声明会导致 `NameError`（在 `fetch_one` 内部首次赋值时）或修改到错误的作用域。

**修复方案**：
```python
# 方案1：使用 nonlocal（Python 3 闭包）
nonlocal success, fail

# 方案2：使用 threading.Lock + 可变容器
success_fail = [0, 0]  # [success, fail]
```

#### Bug 2：`save_to_excel()` 中 `DIMENSION_FILLS` 和 `COL_DIMENSIONS` 重复定义

**位置**：`main.py` 第 450-481 行 vs 第 500-522 行

**问题**：两个字典在函数内定义了两次，第二次覆盖第一次。第一次定义中缺少 `total_score`/`rating`/`confidence` 的映射，如果单独使用会导致 KeyError。

**修复方案**：删除第一次定义（第 450-481 行），只保留第二次。

### 🟡 P1 — 功能缺陷（影响结果正确性）

#### Bug 3：Mock 模式与真实模式的市值单位不一致

**位置**：`main.py` 第 42 行 vs 第 246 行

```python
# MOCK_DATA 中 total_mv 单位是"亿"
'total_mv': 25000.0,

# MockQuote 中 total_mv 单位是"元"（mv * 1e8）
self['total_mv'] = mv * 100000000
```

**后果**：Mock 模式下的 FCF 收益率计算结果与真实模式不一致，评分结果不可比较。

#### Bug 4：`ann_date` 估算过于粗糙

**位置**：`data_provider.py` 第 187 行

```python
df['ann_date'] = df['report_date'] + pd.Timedelta(days=45)
```

**问题**：所有财报统一加 45 天。实际年报公告期 1-4 月（1-2 个月），中报 7-8 月。可能导致回测时引入未来函数或丢失有效数据。

#### Bug 5：同比计算依赖精确日期匹配

**位置**：`calculator.py` 第 144 行

```python
prev_rows = df[df['report_date'] == last_year_date]
```

**问题**：财报日期可能因周末/节假日偏移，精确匹配会失败，导致同比为 0。

**修复方案**：改为 `df[df['report_date'] <= last_year_date].tail(1)`

### 🟢 P2 — 代码质量（不影响运行，但影响维护）

#### Bug 6：双缓存/双数据库系统冗余

| 系统 | 文件 | 数据库 | 存储格式 |
|------|------|--------|----------|
| `DataCache` | `utils_cache.py` | `scoresys_cache.db` | JSON 列 |
| `StockDatabase` | `database.py` | `stock_data.db` | 关系表 |
| `BatchRunner` | `batch_runner.py` | `.cache/*.json` + checkpoint | JSON 文件 |

三个系统存储了相同类型的数据，schema 完全不同，使用时容易混淆。

**建议**：统一为一个数据库系统，推荐 `StockDatabase`。

#### Bug 7：`batch_runner.py` 未集成到 `main.py`

`batch_runner.py` 设计完善（断点续跑 + 限流 + 缓存），但 `main.py` 自己实现了另一套并发逻辑，导致 `batch_runner.py` 成为死代码。

#### Bug 8：`fcf_yield` 计算方式不一致

```python
# calculator.py 中（除以股东权益）
@property
def fcf_yield(self):
    return (self._ttm_ocf - self._ttm_capex) / self._equity_parent

# scorer.py 中（除以总市值）
fcf_yield = (self.ind.fcf_ttm / self.quote['total_mv'])
```

两个模块用不同公式，`calculator.py` 的 `fcf_yield` property 实际未被 `scorer.py` 使用。

#### Bug 9：`main.py` 职责过重（~800 行）

包含 CLI 解析 + 模拟数据 + 批量评估 + Excel 导出 + 多模式运行逻辑，建议拆分。

## 七、总结

这是一个**设计思路正确、核心功能可用**的 A 股量化选股系统。五维评分模型的权重分配合理（盈利 30% > 成长 25% > 现金流 20% > 偿债 15% > 估值 10%），一票否决机制覆盖了主要风险场景，防未来函数设计保证了回测的可信度。

**核心问题**：
1. 一个会导致崩溃的 bug（`global` 引用错误）
2. 双缓存系统冗余带来的维护成本
3. `main.py` 过于庞大影响可读性
4. 行业中性化框架已有但未启用

修复 P0 bug 后，系统可以稳定运行。后续建议按 P1 → P2 的顺序逐步重构。
